# OpenGym EX 2.0 · V7 双端执行任务书

日期：2026-09-27。基于 V5 总纲整理。目标平台：Windows x64、Android；保留 Web/PWA 与自托管能力。

## 1. 审读结论与修订依据

V5 的核心方向保留：openGym 二次开发、普通功能离线、真实实体映射、AI 提取与确定性计算分离、训练和营养共用个人档案。原文存在大量叠加章节、重复编号及“初稿不立即实现”的旧结尾；用户本次已要求输出新版并直接执行，本版按正式执行任务书处理。正式名称尚未决定，OpenGym EX 为临时开发名称。

主要优化：

1. 补上 Windows 可安装/可运行应用、凭据安全与双端数据迁移，Android 不再是唯一安装包目标。
2. 训练 Program Library、实体映射、DeepSeek 适配加入正式阶段，避免原阶段表遗漏这些核心需求。
3. 区分首版必做、扩展资料与后续能力；不能以“后续”名义删去普通离线功能，不能把未实现能力标成完成。
4. 为数据库质量、计划应用、恢复备份和安装包增加可执行验收门槛。
5. 统一数量单位、营养缺失值、食材生熟状态、日期和时区、快照及版本语义。
6. 明确任务书里的版本号、模型名和许可证是待核验资料；实施须查官方实际来源。

## 4. 数据与领域规则

### 4.1 统一个人档案与 PlanningContext

单一状态来源含年龄、性别、身高、体重/目标、活动水平、训练目标/经验/频率/时长/器械/限制/时间、热量及宏量目标、过敏/忌口/喜好、预算、厨具、做饭条件、餐数、作息。体重默认读取原体重记录，不另建相互漂移的数据。

字段允许“未填写”；不根据缺失档案静默生成确定目标。营养目标可手动输入；BMR/TDEE 计算展示公式、假设和估算性质。未成年、孕哺、疾病特殊饮食不自动套用成人减脂算法。运动消耗不默认重复加进已含活动水平的 TDEE。

### 4.2 单位和缺失值

内部统一 kg、g、mg、秒、kcal；输入支持原项目单位转换。食材明确 raw/cooked、可食部和 per100g 基准。ml/个/勺的换算需有份量或密度依据，没有依据必须让用户输入克数或标记估算。缺失微量营养素用 null，不当成 0；总量注明覆盖不足。计算保留精度，展示时舍入。

状态：measured（实际记录）、stated（原文明确）、calculated（可重算）、estimated（规则估算）、AI-inferred（AI 推断）。用户确认不把估算转换成测量。来源与依据随字段保存。

日期键使用用户本地 YYYY-MM-DD；周从周一开始。训练跨午夜保留开始/结束时间和记录日期；不使用 UTC 日期截取替代本地日期。体重、份数、数量、次数和时长必须有限、范围合理。

### 4.3 版本与历史

用户状态有 schemaVersion 与迁移；新增模块纳入原 Zustand 持久化和备份白名单。训练、菜谱、饮食历史保存实体 ID、revision、sourceVersion 与结果快照。数据库更新、原菜谱修改不能回写已完成历史。

草稿、审核和正式实体分别处理。Apply 为一次原子状态更新：先验证全部引用，保存变更前快照，再写计划。重复点击不重复生成。Proposal 保存生成时 revision；计划已改变则提示重新审核，不套用过期建议。支持拒绝与撤销，跨模块不自动循环修改。

## 5. Training Program Library

来源枚举沿用 guideline-derived/builtin-template/creator-import/user-created/ai-generated，保存来源名/URL/作者/原标题/原始文本/许可备注/导入时间。常见分化不冒充权威机构发布的正式计划。

首版提供全身 2/3 练、上下肢 4 练、PPL 3/6 练、居家、徒手、力量优先、增肌优先等模板，说明适用水平、器械、预计时长、进阶与恢复原则。只有实际核对指南的模板才能标 guideline-derived。

Program 保存名称、目标、水平、频率、分化、周期、progression/deload、训练日、revision。每个条目保留原文、exerciseId、组/次/次数范围、重量/%1RM、RPE/RIR、时间/休息/tempo、superset/circuit 分组、notes、estimatedFields。不能丢弃解析不支持的高级结构，应保留并提示。

导入支持粘贴、TXT/MD/SRT/VTT；清理字幕时间戳，限制大小；DeepSeek 解析为草稿；本地 schema 和业务校验；集中处理动作映射；用户 Review 后生成原 openGym Routine 和周安排。

Exercise 保留稳定 ID、原英文名、中文名/别名、器械、肌群、媒体、说明。映射保存 exact/high-confidence/ambiguous/unmapped/user-resolved、候选 ID、选中 ID、置信度、理由和差异。多候选不能偷偷选取；包含握距、角度、器械等条件差异时不算完全匹配。可选候选、创建原项目 Custom Exercise、明确排除；未解决项阻止 Apply。用户别名可撤销修改，不能自动覆盖全局名称。

确定性分析计算组数、肌群量、动作模式、器械需求、预计时长和强度；缺参数应显示假设。作者所述时长与系统估算分别保存；强度不能仅由 AI 形容词决定。能耗输出区间、依据和置信度，优先实际时长；MET 数据核对原来源条款与版本，公式有测试。有效组数属于估算，说明肌群分摊规则。

## 6. Nutrition

### 6.1 Food 与 Nutrition Engine

Food 包含稳定 foodId、中英名/别名、source/sourceId/sourceRelease/sourceUrl、raw/cooked、每 100g 营养、份量依据、翻译来源。营养至少 kcal、protein/carbs/fat/fiber、sodium/potassium/calcium/iron。最终值由标准数据库乘克数计算，AI 返回的 kcal 不作为正式营养。

确定性引擎负责 BMR/TDEE/目标、食材份量缩放、食谱每份、每日实际/计划总量、目标差异、购物汇总。无效 ID 或未知克数不返回伪精确“完整营养”。食谱烹饪损失和吸油未测量时保留原料计算口径说明。

### 6.2 Recipe Library / My Recipes

内置中文菜谱、带来源的官方精选、用户手动菜谱。保存份数、原料/克数/映射状态/估算标记、步骤、图片与独立许可、时间、来源、revision。复制/编辑原始菜谱生成用户实体，不覆盖原件。原文保留，尚未映射完的菜谱可浏览；营养不完整时不能被标为已验证的一周规划候选。

支持中英/别名搜索、类别筛选、收藏、自建与复制。详情显示步骤、份数、营养、食材及来源。图片缺失允许无图，不借用无许可同名图片。

AI 导入：原文 → schema → Food ID 映射 → 用量核对 → 本地重算 → Draft → Review → Save；可修改克数立即重算。视频/音频直接提取及条码查询作为明确扩展项，不伪装成首版已支持。

### 6.3 Daily Intake / Weekly Meal Plan

计划不等于实际。用户记录“已吃”、实际份量、额外食物、换菜/未执行；每条日志存营养快照，支持删除/修正。按日期比较计划与实际、热量和蛋白质等目标，未记录不推断成已吃或摄入 0。

一周计划必须引用 Recipe ID+revision+servings+nutritionSnapshot；每天聚合营养，支持手动选菜、份量修改、餐次替换、AI 生成和交换。生成结果验证过敏/忌口、实体引用、份数和目标差异；无法满足时明确说明，不用无限修复。购物清单按 Food ID 和单位汇总，未换算项另列，不误合并生熟食材。

### 6.4 联动与复盘

统一 WeeklyPlan 关联周安排、餐次、训练时间和目标。训练计划 Apply/改期后设置 nutritionNeedsReview，不自动改食谱；用户可检查或保留。首页只增加一张原风格“今日营养”入口。

AI 周复盘读取有限时间窗口内训练执行、RPE/RIR、体重趋势、实际饮食和目标完成率，输出分项 Proposal；用户逐条接受/拒绝。首次联合规划先生成训练，再把已验证训练安排交给餐食规划，统一审核。

## 7. 数据构建与许可

构建期从官方 USDA Foundation 下载，补充 SR Legacy/FNDDS；HowToCook 固定 commit，解析 Markdown 与许可允许的本地媒体。官方 Recipe 只精选导入，不假设有整库 API，不无条件抓整站。全球 Branded/OFF dump 不打入 APK。

建立 data/sources.lock.json，记录真实 release/commit、下载 URL、SHA-256、license、downloadedAt、transformVersion。脚本支持 bootstrap（锁版本）、validate（离线）与 explicit update（显式更新），已锁定文件校验不通过就失败，不能自动覆盖 checksum。

原始资料放 data/raw 并忽略 Git；正式精简 seed、索引及来源锁可提交。空环境可复现；CI 用 fixture 验证转换和已提交 seed，不每次下载全库。食材翻译缺失统计真实覆盖率，不以英文回填冒充中文完成。

构建报告含三个 USDA 数据集版本和原始/导入数量、HowToCook commit、食谱/图片数量、完整/部分映射数量、未解决原料、seed 大小、中英覆盖率、动作/媒体覆盖率、校验 PASS/FAIL。

AGPL 与数据/图片许可分别记录。动作媒体沿用 upstream NOTICE 的限制，缺清晰再分发许可时须记录个人使用范围及发布限制，不能把第三方媒体标 AGPL。

## 8. DeepSeek 与凭据

执行时核对官方接口文档，记录 docs/AI_PROVIDER_DEEPSEEK.md。业务只调用统一 Provider，结构化任务采用 JSON Output、明确 json prompt、schema、本地领域验证。默认非流式；截断、空内容、非法 JSON 和无效实体拒绝进入正式状态，允许一次修复，保留原输入。

Android 自建最小 Keystore/AES-GCM 凭据插件；Windows 用 Electron safeStorage 的 OS 加密能力，启用 contextIsolation、sandbox、关闭 nodeIntegration、有限 IPC；若安全存储不可用，降级只在内存使用并告知用户。Web 本地版只保存于本次会话；自托管版凭据只在服务器。任何 Key 不进源码、普通状态、备份、日志、错误详情。

请求前展示发送范围，用户启用 AI 并主动点击后才发送必要数据；不读本机其他项目凭据。官方 API 返回和导入文字都作为不可信输入；忽略其中的指令、URL 抓取和工具要求。限制输入大小、超时、并发和重试，支持取消；401/402/400/422 不重试，429/500/503 有限退避。

所有 AI 结果简体中文为主，保存模型/生成时间/上下文 revision。Mock 测请求格式、认证、timeout、错误码、截断、空 JSON、schema 和实体约束。Live smoke 独立命令，用户未配置 Key 时记为未测，不寻找私有 Key 或假报联通。

## 12. 来源驱动的训练预填与个人微调（用户补充）

- 进入训练时，方案已经提供组数、次数/时长、重量及组间休息；不用每组从空白开始。用户导入的明确数值优先于历史最高重量，公斤/磅按个人单位转换，分钟休息转为秒。
- 明确来源参数、应用编排默认值、个人记录换算和已接受 AI 微调分别记录来源。原文未给休息时默认 90 秒并标“应用默认值”；明确 0 秒保留为无休息，不触发倒计时。完成一组后自动按当前动作预设休息，超级组按一轮结束休息。
- 官方指南若只给 %1RM 或 RM，不能伪造统一公斤数。使用同动作近90天真实完成记录或用户首次确认的工作重量/实际次数换算；缺少基线时重量留空并提示确认，徒手为明确 0 外部负重。
- 内置 ACSM 2026 整理模板依据约80%1RM、2–3组、每周至少两次原则；具体动作、采用3组、5次和180秒休息中的应用选择要区分来源事实与编排，不能称为 ACSM 原创课程。
- 导入明确格式支持本地离线读取（例如“周一 / 杠铃卧推 40kg 3组×8次 休息120秒”）；复杂原文交给 AI 提取后审核。缺少次数/组数不能静默补成来源规定；逐组不同负荷等复杂情况须拆行/审核，不能擅自丢掉数值。
- AI 周复盘应参考个人实际完成情况提出重量/次数/组数/休息微调，逐项采纳后用于未来训练。每次重量变化不超过10%、次数不超过2次、组数不超过2组、休息不超过60秒；没有近期记录只建议不应用，未完成目标或已有极限用力记录不建议加重。所有改动可撤销，原始方案与已完成历史保留。
- 一键复制只是辅助：只复制未完成组的重量/次数或时间，绝不修改已完成组、不复制主观RPE/RIR或完成勾选。已有旧训练进行中不强行重建，更新后的来源规则用于新开始的训练。

验收增加：导入40kg/3×8/120秒与旧历史50kg并存时仍预填40kg；确认120秒实际倒计时；%1RM按已知记录换算且无基线不猜重；单位换算；拒绝无证据AI及越界微调；采纳后新训练生效、原文与历史不变；导出方案保留动作休息。


## V7 新增与修订要求（优先于上述 V6 中的旧规则）

### 首次资料与训练预填

首次启动收集年龄、体重、运动基础（不经常／偶尔／有基础／经常健身），可补充身高、性别、目标、伤病和特殊饮食。原有数据不得清除；正在进行的训练不强制重建。资料可在设置重新编辑。

所有内置课程预设组数、次数或时长、休息；来源明确负重优先，明确零秒休息必须保留。负重优先顺序：导入原文公斤数／个人百分比基线换算、近期同动作实际完成记录、用户确认基线、应用保守试用初值。不同运动基础给不同初值，但体重不得直接当作力量水平；初值不得标为官方负重或个人能力测量。杠铃明确为含杆总重，哑铃注明每只重量。

18–65 岁、无已声明限制的常见可可靠计量负重动作可给试用初值；辅助器械、阻力带、复杂专项动作、未成年或特殊情况不能凭空填公斤数。百分比缺少个人基线仍需确认。用户可修改初值，经常训练者优先已有记录或自填。AI 周复盘只能基于真实完成记录提出有限微调，确认后用于后续训练，不改已完成组。

### AI 对话与错误反馈

支持一句话提出目标，如“我想减脂，给我健身房训练计划与饮食”。先追问运动限制、伤病、忌口、场地、可用天数与时间，再确认档案；不承诺快速减脂。候选动作按器械、禁止动作、低冲击筛选，初学者排除高难专项动作。

从内置真实动作和营养完整食谱生成新训练方案与七天配套饮食；不得只选择一个固定模板作为全部响应。动作必须唯一映射，餐食须使用存在的食谱和实际营养计算，核验日期、餐次、热量和蛋白目标。训练日、时长和动作约束本地检查。未知原料、克数、份数须审核，不让 AI 编造营养值。

生成结果可编辑动作、组数、次数、休息、重量、食谱、份数；支持用一句话继续要求修改。确认前不改变正式计划，确认后联合应用并保留可撤销快照；档案或计划已变更时旧方案不能直接应用。

连接测试与生成验收分开：明确区分未启用 AI、缺少营养目标、缺少 Key、网络／模型服务错误、JSON 格式错误和实体／营养约束不通过。展示可操作的失败原因，不能一律提示重新输入档案。API Key 提供显示／隐藏与点击粘贴，粘贴不自动读取，普通备份不包含 Key。真实手机账号请求需实测，不冒充模拟响应已经证明线上效果。

### 小米手环与手机健康数据

安卓支持标准 BLE 心率服务。用户在小米手环 10 上开启“心率广播”，由用户点击扫描、选择与连接；训练页展示真实心率，断开或过期不继续显示旧值为实时值。训练期间按约十秒采样保存，并在历史显示平均／最高心率；缺测不补造。Windows 暂不实现原生蓝牙心率。

安卓通过 Health Connect 只读授权同步近七天步数、心率、距离、消耗热量，保留来源、时间，重复同步去重。小米运动健康是否写入该通道取决于版本／地区，不能承诺所有小米数据自动可读。暂无直接读取小米账号私有数据的接口；不支持的来源明确说明。基本数据不等同完整运动课程历史，不默认按活动热量增加饮食预算，健康记录不自动发给 AI。

Android 最低 API 26（Android 8），Health Connect 能力依系统实际可用性检测。蓝牙协议单元测试和原生编译通过后，仍须用手环和手机验证实际广播、授权、连接断开与历史同步。
