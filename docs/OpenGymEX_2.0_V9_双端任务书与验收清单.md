# OpenGym EX 2.0 · V9 双端任务书与验收清单

整理日期：2026-09-30。当前阶段版本：2.0.5，Android 2.0.5-dev / 20005。正式名称待定。

本版将 V8 的项目范围与用户最新反馈合并为当前执行依据。V6/V7/V8 保存历史，不再以其中的旧名称、长确认表或“所有图片已经高清”作为当前要求。换机步骤另见 [新电脑接手说明](新电脑接手说明与后续任务书.md)，产物和实际验证见 [DELIVERY_STATUS](DELIVERY_STATUS.md)。

## 一、目标与边界

在原 openGym 上完善个人训练与饮食管理，交付 Windows x64 和 Android 可独立运行的应用。保留原训练引擎、训练历史、体重、统计、RPE/RIR、超级组、计时和进阶，不另建一套互不联动的训练系统。普通功能离线；AI 和可选在线菜谱由用户主动使用。

源代码来自 alexpcosta/opengym，保留完整 Git 历史、AGPL、NOTICE 和原作者。私人开发备份仓库为 PLA0185/xunlian-2。保留原自托管能力；个人双端不要求先部署 Docker 或后端，不声称已有自动云同步。跨端个人记录目前通过相同格式 JSON 导出/恢复。

用户已授权正常个人打包、继续完善和私人仓库阶段备份，包括安装包、素材缓存与换机材料。Gymvisual 授权由用户取得；这不等于公开媒体发行授权。API Key 与个人健康资料不因项目备份自动上传；签名材料以单独加密的换机包备份，恢复口令单独携带。

## 二、用户最新使用流程

1. 首次填写年龄、体重、运动基础；身高、性别等可补充。已存在资料和训练不清除。
2. 一句话告诉教练目标、健身时间、上班时间和饮食要求。
3. 固定产品提示词读取原话、已有档案和回答；只补问缺少的必要信息，最多三个合并问题，条件完整就不问。
4. 回答后直接出训练与饮食结果；取消重复身体/星期/忌口长表和“已确认”开关，不再追加第二轮问题。
5. 默认天数、时长、禁止跑跳不能覆盖用户条件。没有指定的安排可由 AI 建议，但必须说明是可修改的建议；身体数据不能猜。
6. 生成结果可以查看、编辑、自然语言修改，离开页面可恢复已生成方案。只有“应用”才替换正式计划，保留撤销；当前训练不会被生成结果覆盖。

“直接出结果”指取消生成前额外确认，不等于自动替换已有正式计划。应用按钮承担实际写入和撤销边界。

## 四、全库做菜与采购验收（本轮新增）

范围是全部402道现有菜谱，不能只给常见组合或只显示菜名。HowToCook原方保留食材清单、数量表/计算、全部操作阶段、原有细节、343个原图引用和完整原文；修复三级标题、加号列表及10道菜的漏食材问题。应用编排配方补充逐道可执行的准备、火候、操作次序、时间/熟制判断及注意事项；非原作者配方须注明应用整理。

点当天餐食、一周餐食、AI方案或联合方案即可打开食材与完整做法；在线预览复用同一做菜组件。做法先于营养明细，手机宽度下材料/数量分列，逐步做菜可上一步、下一步、做完。已安排与已吃记录保留做法快照；后续编辑/删除菜谱不改旧餐食依据。

采购必须按Food ID合并而非按模糊中文合并，生熟与可食重量要清楚，不能把一公斤熟饭当一公斤干米。每项独立大勾选框，名称、用量、说明分行；买完归入已购买，允许取消，重启/备份恢复保留。勾选按周及当时需求量保存；份数/餐食改变导致用量变化要重新核对，最多保留12周勾选。原方未知用量不能填假克数来凑清单，单独提醒核对。

“有做法”与“精确营养可规划”分别统计：402道都有食材与操作说明；29道完整营养可自动安排，373道原方份数尚需审核，2321个原料映射未完成（本轮恢复漏项后真实计数增加）。这些菜全部可以阅读和复制编辑，不能冒充都已精确营养审核。

本轮已读官方食物安全温度表，应用肉类做法引用其熟制判断：[FoodSafety.gov官方温度表](https://www.foodsafety.gov/food-safety-charts/safe-minimum-internal-temperatures)。时间是应用估算，不能直接按份数倍增，也不以固定分钟数代替实际熟制判断。

## 五、领域规则

### 训练与来源

导入明确参数不得丢掉或被历史最大重量替换。单位内部规范化为 kg、秒；保留原输入单位。组间休息缺失时采用标明来源的90秒应用默认，原文零秒必须保留。重量缺来源时，优先近期同动作已完成记录/个人基线；符合条件的常见负重动作可用保守试练建议。杠铃注明含杆总重，哑铃注明每只。体重不能直接推算力量。

百分比需要个人基线；未成年、特殊医疗/孕期、复杂辅助器械等不套用成人自动编排。不能把未知重量当完成的真实记录。AI 微调只有实际证据才可应用：重量最多10%、次数2次、组数2组、休息60秒；失败/极限用力不建议加重。复制只影响未完成组，不复制完成勾选或RPE/RIR。

训练导入保留 sourceLine、originalText 与高级结构。离线解析不支持的复杂周期、逐组变载等必须提示审核，不能悄悄压成统一数值。动作相近名称不能偷偷映射；用户选择后记录个人别名，原数据名称不改。

### 营养与费用

Food 使用稳定 ID、原英文描述、生熟/部位、来源版本、per100g 与缺失值。负值不能产生负摄入，也不能直接篡成零；保留原始 sourceAnomalies，参与计算的字段为 null。食谱份数/克数未知须审核；373条来源原方不因为已经导入就被标为精确营养完整。

规划只使用完整候选。程序先验证日期、实体、餐次、忌口，再按真实营养校准份数；仍不可行时使用经过相同检查的本地组合并说明替换日期。不存在、重复槽位或禁食实体不能用“校准”蒙混通过。无法同时满足数据/限制时明确说明，不无限重试，不生成假营养。

餐数、重复上限、素食、做饭时间来自明确档案或原话。做饭时间为有标注的估算/用户值，未知时间不能冒充满足上限。费用使用对应生熟食材ID的用户价格；只计算原料，不默认包含外卖、人工、水电。价格缺失保留未知，明确标明预算未验证；已知价格时校验每日上限。费用和营养保存快照，改价格/食谱不能改旧记录。

历史与正式计划采用一次原子应用、revision 检查和变更前快照。正式记录与生成草稿分离，取消生成或关闭审核不改已有计划。日期使用本地日期，训练跨午夜保留真实时间。

## 六、AI 提示词与错误处理

产品必要提示词集中在 `frontend/src/lib/coach-workflow.js`，禁止页面另加隐藏硬条件。`brief` 提取已有条件并补缺；`coach` 编排；候选实体、目标和餐次由应用供应，必须通过 schema 和领域校验。最近一句修改优先于旧回答，其他明确条件继续保留。新生成重量不替代个人实际记录。

只有伤病/避开动作、过敏忌口/特殊饮食及确实缺少的必要身体资料值得补问。场地、每周时间、通勤、早餐等已知信息不重复填写。用户没有指定星期或时长时允许提出清楚的建议，不把建议写成用户陈述。提取回答后不再次追问。

区分连接/账号、格式、实体和约束错误。一次结构修复仍失败的提取可显示必要的本地补问；这不是伪造AI回应。营养超差优先程序校准，不能因此要求用户重输Key。网络、超时、取消和费用错误保留用户输入。没有使用用户真实Key的开发验证必须标为模拟。

模型名、接口和依赖按官方文档及锁文件使用，不因旧印象随手更改。Key 不进入源码/状态备份/日志/错误详情；只发送任务所需资料。来源文字/接口响应不能执行网址、命令或更改系统规则。

## 七、媒体与资料质量

用户确认未找到更高清包，当前先使用现有素材。180×180 动画不标为真实高清；11个动作的分解照片不算整库高清。AI静图/GIF仅试做样例，存在技术细节变化，未授权批量替换。

后续取得真实高清包时，按1324稳定ID/英文名映射，短边≥720、多帧GIF、完整覆盖、哈希与人工动作检查，详见 HD_MEDIA_IMPORT。当前高清导入通道和缺失报告已就绪；没有素材不能宣布“所有高清完成”。

1324 动作中文已完整；13,545食材只有85条精确人工中文，其余为类别中文与保留英文细名。不得把类别翻译当精确全中文，也不能删除生熟/部位区别。中国指导资料以国家体育总局、国家卫健委、军报/中国军网等已记录来源为准；指南原则与应用动作/公斤/训练日分开，不把军队考核当普通新手默认强度。
